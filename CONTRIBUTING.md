# Contributing

Thank you for helping make sprite animation more repeatable and inspectable.

The project is experimental and licensed under [MIT](LICENSE). Use [issues](https://github.com/brayan-carlo/tower-sprite-pipeline/issues) for reproducible bugs or focused proposals. No full-suite CI coverage is claimed.

## Start with a small, reproducible problem

For a bug report, include:

1. The publication version or commit.
2. The action, direction, frame count, timing, and chosen workflow.
3. The expected result and the observed result.
4. A source image and minimal output excerpt only when you can legally share them.
5. The operating system, runtime versions, and redacted diagnostic information.
6. Whether the problem occurred offline or required a provider request.

Never include API keys, tokens, personal file paths, private account details, or raw provider receipts. Review attachments as well as text.

For a visual defect, name the affected frames and the concrete observation: changing torso scale, detached grip, missing support alternation, halo, clipping, or a discontinuous loop. A canvas measurement alone does not prove anatomical consistency.

## Propose a change

Explain the problem and keep the patch focused. Preserve originals, durable job identity, shared budget history, and the distinction between technical checks and visual acceptance.

Do not resolve a failed review by weakening its criteria or by marking an uninspected artifact as approved. Do not introduce implicit paid calls into offline checks.

Include a meaningful regression for a code defect where feasible. Report exactly which checks ran and what remains untested.

Use the exact commands and limitations in [VALIDATION.md](docs/VALIDATION.md). The publication ran selected offline tests; it does not claim the entire historical suite passed.

## New evaluation examples

State where the artwork came from, who can redistribute it, and under which terms. Keep code and media licensing separate.

Describe the intended motion and the observed result. New examples should help expose limits, not only repeat cases that already worked.

## Ideas and discussion

Use focused proposals: the user problem, an example, the expected improvement, and the tradeoffs. A provider change should identify what defect it is expected to address and how it would be evaluated.

The maintainer should separate design discussion from reproducible bug reports, and keep starter tasks small enough to review.


## Contribution terms

Submit only material you are entitled to contribute. Contributions to this project's original code and documentation are proposed under its MIT license. Declare any third-party code, schema material, or media and preserve applicable notices.

Spanish and English reports are welcome. A clear reproduction matters more than polished English.
